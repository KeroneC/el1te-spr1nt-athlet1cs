# Seasonal registration and returning check-in

The Registration page has two parent/guardian paths and shows only the selected form. New applications collect athlete eligibility and school details, guardian and household information, an emergency contact, and track background. A previous track club marked Yes requires the last meet month and year; the form does not ask about practice attendance. Returning check-ins still ask only for guardian email and athlete first name, with no paperwork. Intake is separate from Contact, athlete accounts, the roster and Square. After SQL saves either submission, the page shows a reference the family can copy. The new-application receipt says that the club will follow up by text, phone, or email; the returning receipt specifies email. The site does not send an automatic confirmation or decision.

## Review and paperwork

- When staff alerts are configured, each newly saved application queues a short email to each configured staff inbox with an Admin Registration link. It contains no athlete name, family contact, receipt code, or other application details. Returning check-ins and exact receipt retries never queue alerts. The site still does not email families automatically. Staff should use the private queue if email delivery is delayed.
- Keep the semicolon-delimited list in the protected production GitHub Environment secret `REGISTRATION_ALERT_RECIPIENTS`; the deployment stores it in Key Vault and configures a reference on the API. Never commit the addresses. Remove that secret and redeploy to disable alerts. The worker retries failed sends independently so a mail failure does not undo an application. A provider timeout can occasionally cause a repeat alert. Existing applications are not backfilled when alerts are enabled.
- Use **New Applications** or **Returning Check-Ins**. Search stays in the private Admin form, not the URL. **Back to queue** preserves the active filters and page; **Clear filters** resets them. Follow up, waitlist, offer, close or reopen as appropriate. Status changes never contact a family; send the decision manually.
- An offer allows paperwork while a prior-club case is unresolved. Verify any applicable AAU and USATF steps outside the app. Do not mark an athlete competition-ready until they are enrolled and transfer review is cleared or not needed.
- Only new athletes offered a spot send paperwork. Explain how to hand in paperwork when the club contacts families after an offer. Do not ask for paperwork at application time or upload completed forms to the app. Photo consent is optional and tracked separately from enrollment. Returning athletes only complete the online check-in; staff can move them from Offered to Enrolled without collecting paperwork.
- Closeout is unavailable until an approved end date is recorded. At least 90 days after that date, the retention owner verifies intake is closed and asks an authorized SuperAdmin to confirm closeout in Season Settings. This permanently removes SQL submission records and linked review history while retaining channel totals. It does not delete club email, paper files, or any copies in existing backups; follow the club’s separate retention procedure for those. Once any TBD season is saved, fix forward with a release that supports a nullable end date; do not redeploy an older API or downgrade the schema. Before demo sign-off, use only synthetic submissions and a clearly labeled season.
