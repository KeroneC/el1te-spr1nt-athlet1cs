# Deployment Documentation

Phase 6B operates a manually approved Azure demo in Central US. Read [CI/CD overview](architecture/cicd-overview.md), [Azure demo continuous delivery](architecture/future-azure-deployment.md), [Azure setup and release](guides/future-azure-setup.md), [observability and support references](guides/observability-support.md), [launch hardening and content promotion](guides/launch-hardening-performance.md), [store and Square foundation](guides/store-square-foundation.md), [public storefront and configurator](guides/store-public-configurator.md), and [Square checkout and order operations](guides/store-square-checkout-orders.md).

The demo enables cookie-free public browser performance telemetry, uses CSP report-only mode, disables anonymous Parent registration, and provisions an Azure-managed Communication Services email sender for Admin MFA and password recovery. `Microsoft.Communication` must be registered once at subscription scope. The workflow reuses an existing registration and attempts registration only when it is missing, so the normal resource-group-scoped deployment identity does not need subscription-level registration permission after bootstrap. Production must enforce CSP only after violation review and must verify the club sender domain before launch. Apply the launch-hardening migration before running the idempotent media derivative backfill. Selective content promotion remains dry-run-only until a separate production environment and a disposable rehearsal are approved.

The demo budget update is idempotent: an existing budget retains its original Azure-managed time period while amount and notification thresholds are reconciled. New deployments create the period only when the budget does not yet exist.

Commerce deployments keep `Store__Enabled=false` and `Store__CheckoutEnabled=false` until the documented demo test gate. The standard demo deployment sets `Store__PublicPreviewEnabled=true`, which exposes the catalog, configurator, and non-personal cart while payment remains disabled. A supervised Sandbox checkout test sets both transactional flags true only after the Square access token, location, exact webhook URL/signature key, return URL, and webhook subscriptions have been verified. Production should keep preview false unless explicitly needed. Square secrets belong in Azure Key Vault and enter App Service only through Key Vault references. Catalog records are created manually in the protected Admin workspace; Square catalog import is not available.
